# Резервное копирование и восстановление на момент времени

Скрипт [`pitr.sh`](pitr.sh) не описывает процедуру, а выполняет её целиком: поднимает
кластер с архивацией WAL, снимает базовый бэкап, пишет строку, запоминает момент,
пишет вторую строку — и восстанавливается на момент между ними. В конце он проверяет
единственное, что имеет значение: первая строка есть, второй нет.

```bash
make pitr          # ~40 секунд, контейнер удаляется в конце
bash backup/pitr.sh --keep   # оставить контейнер, чтобы посмотреть изнутри
```

Ниже — вывод настоящего прогона, не пример.

## Устройство

```
        живой кластер (порт 5432)                восстановленный (порт 5433)
        ─────────────────────────                ───────────────────────────
  T0    CREATE TABLE receipts
        INSERT 'seeded before the backup'
  T1    pg_basebackup ──────────────────────────► /var/lib/postgresql/basebackup
  T2    INSERT 'written before the target'
  T3    ◄── recovery_target_time = now()
  T4    INSERT 'written after the target'
  T5    pg_switch_wal() ────────────────────────► /var/lib/postgresql/archive
                                                   restore_command читает отсюда
  T6                                               pg_ctl start -o "-p 5433"
                                                   восстановление до T3, promote
```

Второй кластер запускается **в том же контейнере на другом порту**. Первый при этом
не останавливается, и оба можно опросить рядом — именно так и выглядит настоящее
восстановление: старая база ещё жива, пока новая догоняет.

Ключевые параметры:

| параметр | значение | зачем |
|---|---|---|
| `wal_level` | `replica` | минимум, при котором WAL пригоден для восстановления |
| `archive_mode` | `on` | требует рестарта, поэтому задаётся при старте кластера |
| `archive_command` | `test ! -f dst && cp src dst` | проверка перед копированием обязательна: PostgreSQL считает успешный код возврата подтверждением, и перезапись существующего сегмента молча разрушает архив |
| `restore_command` | `cp archive/%f %p` | обратная операция при восстановлении |
| `recovery_target_time` | момент между двумя вставками | граница восстановления |
| `recovery_target_action` | `promote` | иначе кластер останется в режиме recovery |
| `archive_mode` в восстановленном | `off` | иначе восстановленный кластер начнёт писать в тот же архив |

`recovery_target_time` — **не** «состояние базы в этот момент», а «последняя
транзакция, зафиксированная не позже этого момента». Разница видна в логе ниже:
PostgreSQL пишет `recovery stopping before commit of transaction 743`, то есть
останавливается **перед** первой транзакцией за границей, а не после последней до неё.
Для транзакции, начавшейся до цели и зафиксированной после, это означает, что её не
будет.


Три строки лога, ради которых всё это и запускается:

- `starting point-in-time recovery to ...` — цель прочитана из
  `postgresql.auto.conf`. Если её там нет, PostgreSQL восстановится до конца WAL и
  честно об этом промолчит;
- `consistent recovery state reached at 0/3000120` — раньше этой точки кластер
  открывать нельзя, backup label указывает именно на неё;
- `recovery stopping before commit of transaction 743` — граница сработала. Если бы
  архива не хватило, вместо этой строки было бы
  `recovery ended before configured recovery target was reached`, и это единственный
  способ отличить «восстановились куда просили» от «восстановились куда смогли».

## Чего этот прогон не доказывает

Скрипт проверяет механику восстановления, а не пригодность процедуры для
эксплуатации. Отдельно нужно:

- **Проверить восстановление на реальном объёме.** 45 МБ восстанавливаются мгновенно.
  RTO определяется не механикой, а размером базы и скоростью чтения архива, и меряется
  только на настоящих данных.
- **Проверить восстановление на другой машине.** Здесь второй кластер стартует в том
  же контейнере и с той же локалью, версией и набором расширений. Восстановление на
  чужой хост ломается именно на этом: отсутствующее расширение, другой major, другая
  сборка ICU.
- **Проверить полноту архива на длинном интервале.** Здесь между бэкапом и целью один
  сегмент WAL. Реальный архив живёт неделями, и его дырки обнаруживаются в момент
  восстановления, а не в момент архивации: `archive_command` вернул ноль — PostgreSQL
  считает сегмент сохранённым и вправе его удалить.
- **Считать WAL за время восстановления.** Точка восстановления в прошлом на сутки
  требует всех сегментов за эти сутки; их объём — это и место в хранилище, и время
  чтения при восстановлении.

`archive_command` из `cp` годится для этой демонстрации и не годится для
эксплуатации: нет fsync каталога архива, нет проверки контрольной суммы, нет ретраев,
нет ротации. В настоящем кластере на этом месте стоит `pgBackRest` или `WAL-G` — и
основная причина не в `cp`, а в том, что они умеют инкрементальные бэкапы, проверку
целостности архива и удержание по срокам, чего у скрипта из двадцати строк не будет
никогда.
